# Broker calls, resources, storage, credentials, and subscriptions

Guest code sends typed `api.request` output and receives the matching typed reply through the protocol. It never calls a Tauri command, Vault, SQLite, SSH transport, SFTP subsystem, or operating-system API directly. `describe` reports the current protocol, platform, available methods, and limits; use it instead of assuming a capability is usable on every platform. The complete request/result matrix is in [Plugin API broker methods](../plugin-api/broker.en.md).

Resources are opaque, owner-scoped, generation-fenced handles. Use `resourcesList`, `resourceEvents`, and `resourceClose`; close is explicit and cancellation, revoke, disable, package replacement, stale scope, or crash can close a resource independently. Timers and event subscriptions are resources. Subscription events are real Core events for terminal metadata, approved Host scope, and plugin settings; poll only when the reference explicitly calls for polling. Do not persist a handle, turn it into a capability, or reuse it after a lifecycle transition.

`storage` is the unified plugin-private JSON store. It is non-secret, bounded, revisioned, and compare-and-swap protected. Do not use an obsolete `plugin_storage`/`pluginStorage` protocol surface, and never put credentials in storage.

`networkStart`/`networkSend` broker HTTP, WSS, TCP, UDP, and TLS as typed resources. The exact target and resolved destination set are frozen before the protected operation; redirects and ambient proxies are not a substitute for a grant. `filePick`/`file` use opaque roots. `sftpOpen`/`sftp` use scoped SFTP resources. `remoteExecStart`/`remoteExecSend` use an independently authenticated bounded remote exec transport; `processStart`/`processSend` use a separately approved local process plan. These operations produce resource events for actual open/data/exit/error/close facts.

`credential` supports plugin-owned accounts through a Vault-protected, host-rendered input path. A plugin receives an opaque reference and non-secret state only. Core injects it solely into the approved exact HTTPS/WSS origin; it cannot be copied into generic requests or plugin storage.

Only an explicit foreground user operation may cause a protected decision. `onOpen`, timer, provider callbacks, automatic task steps, restart recovery, and CLI harness traffic must return a typed non-interactive outcome instead. In particular, `vaultMissing`, `vaultLocked`, and `vaultRequiresReload` are states to surface to an explicit user action, never a license for background create/unlock. `once` applies to the current pending exact operation; `always` can be retained only for a Core-calculated exact operation and remains revocable and execution-fenced.

The protected prompt defaults to “Allow once”. Only when Core reports `exactOperation` can the user select “Always allow this operation” and choose 15 minutes, 1 hour, 24 hours, or unlimited (the default). The host renders the risk disclosure and expiry controls; the guest cannot retain or select approval on the user’s behalf. Core stores a nullable absolute expiry instead of a duration, so restart cannot extend it. There is no general permission-scope database for network, files, or serial devices: each retained rule fingerprints the frozen request. Guest-visible permission rows are current-owner summaries only. File and serial selections use opaque management labels; raw canonical paths and device identities stay in the active Core scope and protected prompt.

Remembered operations and capability grants are separate checks: an exact retained rule cannot supply a missing or revoked capability. `permissions` returns current-package non-secret summaries and `policyRevision`; `permissionRevoke` must carry the revision just read, while `permissionsForget` removes operation rules owned by the current guest. Revoking an operation rule neither revokes nor expands a capability grant. Users can also inspect expiry and revoke through the installed plugin’s **More → Operation permissions** dialog; revocation requires no new approval. See [Capabilities and protected operations](../plugin-api/capabilities.en.md).
